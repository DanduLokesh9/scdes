Technical Overview

The AI Governance application — how it is built, in plain English
14 August 2026 · https://app.staging.governingai.us

In one paragraph. An agency writes its AI rules into Word and Excel documents and adopts them. This application reads those documents and turns them into working software: it answers questions about the rules with exact citations, scores projects for risk using the agency's own weightings, and walks a project through the approval gates while filling in the real spreadsheets. Nothing about the rules is written into the code. Point it at a different agency's documents and it becomes that agency's application.

1. The shape of it

Two halves, as with most web applications:

HalfWhat it doesWritten in
Back end Runs on the server. Reads the documents, does the thinking — risk scoring, searching, permissions, record-keeping — and answers questions from the front end. Python (24 files, ~7,300 lines)
Front end Runs in the browser. Everything you see and click. Holds no rules of its own; it asks the back end for everything and draws the answer. HTML, CSS, JavaScript (8 files, ~3,000 lines)

They talk over 29 web addresses (called endpoints). The browser asks /api/registry and gets back the list of projects; it asks /api/budget and gets the money figures. Plain messages in, plain messages out.

Why the split matters. All the judgement lives in one half. The browser cannot decide that a project is Low risk or that someone may approve a gate — it can only display what the server said. Anyone who tampers with the page in their browser changes what they see and nothing about the record.

2. The back end, file by file

Grouped by what each one is for, rather than alphabetically.

Reading the agency's documents

FileWhat it doesLines
ingest_xlsx.py Reads the Excel appendices and works out which cells are questions, which are answers, and which are tables. A spreadsheet does not know it is a form; this is what teaches the software to see one.595
ingest_docx.py Reads the Word documents and splits them at their own headings, so every chunk of text is a complete numbered section — which is what makes citations exact.222
profile.py Works out whose documents these are: the agency's name, its instruments, its approval gates, its roles. This is what lets the same software serve any agency.588
vocabulary.py Counts how the documents actually name things — "Category 1" versus "Bucket 1" — and makes every screen use the winner.290

Two pieces of artwork worth mentioning

  • The map (135 KB). Real geography — US Census boundary data, drawn with the standard projection for the continental US, with Alaska and Hawaii as insets. Built once, offline. No mapping service, no internet, no account needed.
  • 51 state flags (1.9 MB). The genuine flags, bundled locally so the app never calls out to the internet. Fifty are public domain; Mississippi's 2020 design is copyrighted with free use granted, and that difference is recorded rather than glossed over.

4. How a click travels through the system

Someone opens the Registry screen. What actually happens:

1. Browser     app.js asks for /api/registry
2. Server      server.py receives it, works out who is asking
3. Permission  authz.py: may this person see the register?  yes
4. Data        registry.py reads the project records from disk
5. Thinking    scoring.py works out each project's risk band
6. Wording     vocabulary.py labels them in the agency's own terms
7. Answer      the server sends back a plain data message
8. Drawing     app.js turns it into the table you see

Steps 3 to 6 are all on the server. The browser receives finished answers, never the rules that produced them.

5. Where everything is kept

There is no database. Everything is ordinary files, which matters for something meant to stand up as a legal record: any of it can be opened and read years later without this software.

WhatWhereSize
Adopted framework (Word)corpus/framework/71 KB
Operations manual (Word)corpus/manual/58 KB

Tuned settingscorpus/config/*.yaml21 KB

Council decisionscouncil/decision_log.jsonl25 KB
Portal registrationsdata/registrations.jsonl—

The .jsonl files are one record per line, in a format that is readable as plain text. The audit trail is the important one: each line includes a fingerprint of the line above it.

What that does and does not prove. Change or delete a past entry and every entry after it stops matching, so the tampering is detected and the exact point named. But someone with access to the file could rewrite the whole chain from the beginning and it would verify cleanly. It is tamper-evident, not tamper-proof. Closing that gap needs a write-once store or digital signatures.

6. What it is built on

PieceChoice
LanguagePython 3.11 or newer
Web serverPython's own built-in one — no Django, Flask or FastAPI
Browser codePlain JavaScript — no React, Vue or Angular
DatabaseNone
Outside librariesThree, all for reading documents: openpyxl (Excel), python-docx (Word), PyYAML (settings)
Internet neededNone. It runs with the network unplugged.
Automated tests794, run in about 13 seconds
Why so few tools. Every framework added is something that must be kept updated for as long as the record must be readable — and a governance record outlives most frameworks. A build with three dependencies can be picked up in five years and still run. It also means an agency's IT department can read the whole thing without learning anybody's framework first.

7. Search, without artificial intelligence

Asking "what triggers a Level 2 incident?" gives an answer citing Operations Manual §22.4. That is not a language model — it is word matching, weighted so that rare specific terms count for more than common ones.

Chosen over an AI-based approach for three reasons: the documents are searched using their own vocabulary, where exact words beat approximate meaning; the passage found is the citation, so the reference is exact rather than plausible; and it needs no model, no service and no internet.

It also refuses. Ask something the documents do not cover and it declines rather than guessing.

An optional language model can be connected to make answers read more smoothly. Even then, the searching and the citing stay local — only the retrieved passage and the question would ever leave the machine.

8. How it serves fifty states

Nothing about South Carolina is written into the code. The agency's name, its instruments, its gates, its roles and its vocabulary are all worked out from whichever documents are loaded.

This was proved rather than assumed: a synthetic agency was invented that shares nothing with SCDES — different state, different instruments named "Schedule 1–5" instead of "Appendix A–N", different checkpoints, different vocabulary — and the software adapts to all of it. A test also searches the code for agency-specific words and fails the build if any appear.

One honest limit. Only one agency's documents are loaded at a time. Selecting Texas on the map changes the theme and the name, but Texas's documents do not exist here. Rather than show South Carolina's projects under a Texas heading — a fabricated record — every screen refuses and explains why.

9. Known limits

  • No log-in security. The sign-in screen establishes who is acting but does not verify it. Anyone with the web address can currently act as the Council. Real authentication, or a password on the site, is needed before it is shared.
  • Registration is not verification. The portal checks an email is on a public-sector or non-profit domain and records the claim. No confirmation message is sent; every entry is marked unverified.
  • The audit trail is tamper-evident, not tamper-proof (§5).
  • Tuning covers 13 of the 1,068 fields the reader finds. The parser reads everything; the tuning screen exposes the parameters that matter most.
  • No live model monitoring exists yet, so the Oversight screen shows a schedule of what is owed rather than invented drift figures.
  • One server, one disk, no backups configured. Worth adding before this holds anything that matters.

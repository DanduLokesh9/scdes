Governing AI — AI Governance application · staging on AWS EC2
Completed 14 August 2026 · https://app.staging.governingai.us

Outcome. The application is live over HTTPS, runs as a managed service that restarts on crash and starts on boot, and its 794 automated tests pass on the server itself. Two infrastructure faults were found and fixed on the way; both are documented below because they are the parts most likely to recur.

2. Pre-flight checks (from the local Windows laptop)

Step 1 — Confirm the SSH key and client

Get-ChildItem "C:\Users\dandu\Downloads\*.pem"
ssh -V

Found govern.pem (1674 bytes). OpenSSH 9.5p2 present. Later confirmed against the console: the instance's Key name is govern, so this was the right key.

Step 2 — Restrict the key's permissions

icacls "C:\Users\dandu\Downloads\govern.pem" /inheritance:r /grant:r "$env:USERNAME:(R)"

SSH refuses to use a private key that other accounts can read. A freshly downloaded .pem inherits broad permissions, so this is required before the first connection, not optional hygiene.

Step 3 — Confirm DNS resolves

Resolve-DnsName app.staging.governingai.us -Type A

Returned 107.21.44.130. The GoDaddy A record was correct throughout and never needed changing.

Step 4 — Test the ports

$c = New-Object System.Net.Sockets.TcpClient
$c.ConnectAsync("107.21.44.130", 22).Wait(6000)

All three ports (22, 80, 443) timed out. A control test against github.com:443 succeeded, proving the fault was at the server end rather than local networking.

Reading the failure mode matters here. A timeout means packets are being silently dropped — a firewall or a dead address. A connection refused would instead mean the host is reachable but nothing is listening on that port. The two point at completely different causes, and distinguishing them saves a great deal of guessing.

3. Fault 1 — Elastic IP not associated

The security group (hazmit-staging-sg, inherited from an earlier project) was checked first and turned out to already allow SSH from 0.0.0.0/0. So the security group was not the cause.

The real cause: the instance had been relaunched, and a newly launched instance does not inherit an Elastic IP. The address 107.21.44.130 was pointing at nothing.

Fix

Console → EC2 → Elastic IPs → select 107.21.44.130 → Actions → Associate Elastic IP address → choose the instance → Associate.

Port 22 answered on the first probe afterwards.

Also added to the security group for later use:

TypePortSourcePurpose
SSH22your IP /32 (or 0.0.0.0/0)administration
HTTP800.0.0.0/0public site, and Certbot's challenge
HTTPS4430.0.0.0/0public site over TLS

Note this security group is shared with another instance, so opening 80/443 opens them there too. A dedicated group avoids that spillover.

4. Fault 2 — no IAM role, so Session Manager could not connect

Two browser-based connection methods were tried before SSH:

  • EC2 Instance Connect — failed with "Error establishing SSH connection". Usually the IAM user lacks ec2-instance-connect:SendSSHPublicKey.
  • Session Manager — the Connect page reported IAM role: – and, in its own diagnostics, "SSM Agent unable to acquire credentials … instance management role is not configured".

Session Manager authenticates through IAM, so it requires an instance role. None was attached.

Fix

  1. EC2 → tick the instance → Actions → Security → Modify IAM role
  2. Create new IAM role → trusted entity AWS service, use case EC2
  3. Attach AmazonSSMManagedInstanceCore (CloudWatchAgentServerPolicy is a harmless extra) — no custom policy needed
  4. Name it instanceRole → Create role
  5. Back on Modify IAM role → refresh → select it → Update
  6. Reboot the instance. The SSM agent caches its credentials and will not pick up a newly attached role otherwise.

Session Manager connected after the reboot.

Step 8 — Supply the GitHub token without recording it

read -s -p "GitHub token: " GH && echo
echo "captured ${#GH} characters"

read -s suppresses echo, so the token is not displayed and does not enter shell history. The length check confirms the paste landed: about 40 characters for a classic ghp_ token, about 93 for a fine-grained one.

6. HTTPS

Step 12 — Issue the certificate

bash deploy/enable_tls.sh you@your-real-email.com

The email is used by Let's Encrypt only to warn of an expiry that failed to renew. Any real mailbox is fine; it need not be on the domain.

Run this only after http:// loads in a browser. Certbot proves control of the name by answering a challenge on port 80 at that exact hostname. If DNS has not propagated, or port 80 is shut, it fails with a message that does not obviously say so — which is why the script checks the name resolves to this host before starting.

7. Certificate renewal — and how it fails

Let's Encrypt certificates last 90 days. Certbot installs a systemd timer that attempts renewal twice daily and acts at about day 60, so in normal operation there is nothing to do. The failure mode is not that renewal is hard; it is that renewal fails silently and the first visible symptom is a browser refusing to load the site.

The single most useful habit. A renewal that has never been tested is not a renewal — it is an assumption with a 90-day fuse. Run sudo certbot renew --dry-run after issuing a certificate, and again any time nginx, the DNS record or the firewall changes. It performs a real renewal against Let's Encrypt's staging endpoint without consuming a certificate, so it can be run freely.

Normal state — verify, don't assume

# Is the timer active, and when did it last run?
sudo systemctl list-timers 'certbot*' --all

# What certificates exist, and when do they expire?
sudo certbot certificates

# Will renewal actually work? This is the one that matters.
sudo certbot renew --dry-run

Expect the dry run to end with "Congratulations, all simulated renewals succeeded". Anything else needs attention now, not in sixty days.

Manual renewal

# Renew only if within the renewal window (does nothing otherwise)
sudo certbot renew

# Force it regardless of the window — use sparingly, there are rate limits
sudo certbot renew --force-renewal

# Then, if certbot did not reload nginx itself
sudo systemctl reload nginx

Let's Encrypt permits 5 duplicate certificates per week for the same set of names. Repeatedly forcing renewal while debugging will exhaust that and lock you out for a week, so debug with --dry-run instead.

Case study: this exact failure, on the sibling server

Worth recording in full, because nothing about it was obvious from the outside and the same latent fault can exist on any server here.

A second staging site, app.staging.hazmit.ai, began showing Chrome's "Your connection is not private" with NET::ERR_CERT_DATE_INVALID. Its certificate had expired 19 days earlier. Diagnosis, in order:

CheckFindingConclusion
Ports 22 / 80 / 443 from outsideall opennot a firewall
http://…/.well-known/acme-challenge/testHTTP 404 from nginxACME can reach the host — a 404 here is a good sign, it proves nginx answered
systemctl list-timers 'certbot*'active, last run 2 hours earlierthe timer was never the problem — it was running and failing
certbot renew --dry-run"Could not bind TCP port 80 because it is already in use"root cause

The cause. The certificate had originally been issued with certbot's standalone authenticator, which starts its own temporary web server on port 80 to answer the challenge. That worked at the time — presumably before nginx was installed. Once nginx held port 80 permanently, certbot could no longer bind it, so every renewal attempt failed on the same error. The timer kept firing and kept failing, daily, for roughly a month.

The fix is to switch the authenticator to the nginx plugin, which cooperates with a running web server instead of needing the port to itself:

sudo apt-get install -y python3-certbot-nginx

# Reissues the certificate AND rewrites the stored renewal configuration
# to use nginx from now on. A plain `certbot renew` would keep using the
# broken standalone method and fail identically.
sudo certbot certonly --nginx -d app.staging.hazmit.ai --force-renewal

# Prove the repair, rather than hoping
sudo certbot renew --dry-run

certonly fetches the certificate without touching the nginx site configuration, so how the site is served is unchanged. The nginx plugin reloads nginx itself, so no separate reload was needed — confirmed by reading the served certificate from outside.

Which authenticator is a certificate using?

sudo grep -H authenticator /etc/letsencrypt/renewal/*.conf

authenticator = nginx or webroot is safe alongside a running web server. authenticator = standalone on a machine running nginx or Apache is a certificate that will silently fail to renew — fix it before it expires, using the commands above with the correct domain.

Recovering an already-expired certificate

The steps are the same; expiry changes nothing about the process, only the urgency. Note that a browser having seen HSTS for the domain will refuse to let anyone click through the warning, so the site is fully unreachable rather than merely alarming — there is no partial degradation to buy time with.

Do not rely on the expiry email

Let's Encrypt emails the address registered with the account before a certificate lapses. In the case above, either that address was stale or the mail went unread, and the failure ran for a month unnoticed. Check what address is on file:

sudo grep -r '"contact"' /etc/letsencrypt/accounts/*/*/regr.json

Better than relying on mail: an uptime check against https:// from outside the server, which fails the moment a certificate does. Or a weekly cron that runs certbot renew --dry-run and alerts on a non-zero exit.

Applying the lesson to every other host

Any certificate issued with --standalone before a web server was installed carries this fault dormant. On each machine:

sudo certbot renew --dry-run

Passing means it is fine. Failing means it will expire, and the error names the reason.

9. Operating it

sudo systemctl status governingai      # is it running?

Deploying an update

cd /opt/governingai
git pull
sudo systemctl restart governingai
Why an update cannot destroy the record. The audit log (corpus/audit/log.jsonl), the registrations (data/registrations.jsonl) and the filled appendix workbooks (corpus/registry/) are written at runtime and are not tracked in git, so git pull leaves them untouched. This matters specifically because the audit log is a hash chain: overwriting it would break the one property the application exists to guarantee.

10. Outstanding — before this URL is shared

The application has no authentication. The sign-in screen establishes who is acting but does not verify it, and the user is carried in a URL parameter. The site is now publicly reachable, so anyone with the address can act as the Council and adopt parameter sets.

The application binds to 127.0.0.1 rather than 0.0.0.0, so nginx is the only route in — that is what makes a password at the proxy effective rather than bypassable on port 8765.

Putting a password on the staging site

sudo apt-get install -y apache2-utils
sudo htpasswd -c /etc/nginx/.htpasswd yourname
sudo nano /etc/nginx/sites-available/governingai
#   uncomment:  auth_basic "Governing AI — staging";
#               auth_basic_user_file /etc/nginx/.htpasswd;
sudo nginx -t && sudo systemctl reload nginx

Both lines are already present in the shipped config, commented, with these instructions above them.

Other known limits

  • Registration is not verification. The portal checks that an email is on a .gov/.org/.us-style domain and records the claim; no confirmation message is sent. Every stored entry is marked verified: false.
  • The audit log is tamper-evident, not tamper-proof. Editing a past entry breaks the chain and is detected, but anyone with file access could rewrite it from the beginning. Closing that needs an append-only store or signatures.
  • Single instance, single disk. Persistence is the root EBS volume. There are no snapshots configured — worth adding before this holds anything that matters.
